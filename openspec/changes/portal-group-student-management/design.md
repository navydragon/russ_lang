# Design

## Context

Мотивация описана в proposal.md. Group и Student уже имеют уникальный code, но не ID портала; Student хранит одну локальную группу, а почта в его модели отсутствует. GroupForm и представления управления доступны is_staff. На странице группы есть только список и подтверждение исключения; students/tests.py пока пуст. Консольный import_students читает XLSX с реквизитами группы, кураторов и студентов, но не создаёт пользователей портала и не сохраняет студенческую почту.

В отдельном репозитории WebSoft API маршрутизатор index.html вызывает libs/<mode>.js. Есть russian_language/get_curator_emails, collections/groups.js умеет добавлять участника без дублей. admin/create_dot_student назначает семестры и потому неприменим целиком. Исходники API используют CP1251. Живой портал не проверялся и не изменялся. Graphify недоступен из-за отсутствующего интерпретатора; выводы основаны на чтении файлов.

## Goals / Non-Goals

**Goals:** один серверный путь записи для модалок и импорта, повторяемость после частичного сбоя, сопоставление без потери существующих результатов.

**Non-Goals:** распределённая транзакция между Django и WebSoft, фоновая двусторонняя репликация, перенос старых данных автоматически, создание семестров и изменение сценария ДОТ. Кураторы остаются локальными: их синхронизация не согласована.

## Decisions

### Серверный адаптер и отдельный модуль портала

Браузер обращается только к Django с обычной сессией и CSRF. Новый сервис students вызывает https://api.emiit.ru/_wt/russian_language/action/{action} с JSON UTF-8 и заголовком Authorization. Базовый URL, токен и таймаут задаются серверными настройками из окружения; значения не попадают в шаблоны, сообщения и логи. На портале каждая новая операция дополнительно проверяет выделенную учётную запись интеграции по настроенному ID; существующий auth:false маршрут чтения не расширяется на запись. Альтернатива прямых запросов браузера отвергнута из-за раскрытия полномочий интеграции.

Предлагаемый контракт (новые маршруты; существующие не меняются):

| Метод | action | Запрос | Успешный результат |
|---|---|---|---|
| POST | upsert_group | code, name | group_id, code, name, status |
| POST | upsert_student | code, login, last_name, first_name, middle_name, email, password только для нового | student_id, code, login, status |
| POST | ensure_membership | group_code, student_code | group_id, student_id, status |
| DELETE | remove_membership | group_code, student_code | status |
| DELETE | delete_group | code | status |

Ответ JSON: {ok:true, data:{...}}; status = created / updated / unchanged / removed. Ошибка: {error:true, status:<HTTP>, code:<машинный код>, message:<без секретов>}. Валидация — 400, авторизация — 401/403, неоднозначность или непустая группа — 409. ID — строки, без преобразования в JS Number. DELETE использует JSON тела, который серверный адаптер передаёт явно. Подтверждение членства возвращает ID обоих объектов. Если оба объекта или членство уже отсутствуют, снятие считается выполненным.

### Ключи и область операций

code группы и code = login студента — неизменяемые ключи после создания; формы редактируют только атрибуты. Убираются внешние пробелы, регистр и ведущие нули сохраняются; коллизии с регистронезависимым поиском портала возвращают 409 вместо объединения пользователей. Если исторические code и login на портале расходятся, операция блокируется с диагностикой. Существующие группы ищутся по code; после однозначного сопоставления получают отметку принадлежности интеграции русского языка. Снятие членства и удаление группы разрешены только для этой области, пользователь может уже существовать на портале.

Добавить nullable уникальные строковые portal_id в Group и Student, email в Student. Старые записи получают ID при первой успешной операции. Локальные студенты сохраняются через update_or_create по code, не пересоздаются вместе с попытками. Альтернатива сопоставления по ФИО или почте отвергнута: эти поля изменяемые.

### Идемпотентность и конкурентная запись

Выбор при реализации: штатный `EvalCs` вокруг всего поиска и изменения. Он проверен на работающем локальном WebSoft: счётчик 16 параллельных запросов не потерял обновлений; параллельные создания группы и студента возвращают один ID. Это общая критическая секция одного экземпляра сервера, более широкая, чем блокировка отдельного ключа. Для кластера независимых экземпляров потребуется блокировка общей БД. В Django используется блокировка файла ОС между процессами одного хоста, автоматически снимаемая при завершении процесса.

Новые маршруты выполняют собственную проверку заголовка авторизации и разрешённого ID интеграции через `russian_roster.authenticate`: при локальном файловом доступе `curUserID`/`curUser` могут не быть инициализированы. Прочие маршруты не меняют существующую авторизацию. Фактический контракт и результат проверок описаны в verification.md.

На API нужен реальный механизм блокировки по ключу группы/пользователя на время поиска и создания (средство блокировки WebSoft либо выделенный уникальный реестр ключей с атомарным захватом). Простая последовательность SELECT + Save без защиты не принимается. Захватить ключ, повторно прочитать запись, проверить неоднозначность, применить изменение, освободить блокировку в finally. Для членства блокируется документ группы; удаление пустой группы проверяет отсутствие участников под той же блокировкой. При занятости возвращается повторяемый 409 busy. Конкретный доступный примитив проверяется небольшим тестом на установленном WebSoft до реализации записи; при его отсутствии нельзя объявлять конкурентную идемпотентность готовой.

Пароль нового пользователя берётся из непустого password либо генерируется криптографически стойким генератором Django и передаётся только на создание. Существующий пароль API не читает и не возвращает, поле password при обновлении игнорирует. Выдача реквизитов и отправка писем не входят в этот change. ФИО и почта берутся из последнего подтверждённого запроса; пустое необязательное поле очищает соответствующий атрибут.

### Порядок записи и восстановление

Для группы: валидация Django, upsert портала, локальная транзакция сохранения атрибутов, кураторов и portal_id. Для студента: upsert пользователя, ensure_membership, затем локальная транзакция. При исключении: remove_membership, затем Student.group = None. При удалении группы: локальная проверка пустоты, delete_group портала, затем локальное удаление.

После таймаута результат портала неизвестен: интерфейс сообщает об этом и предлагает повторить ту же операцию. При успехе API и сбое БД повтор выполняет те же действия и завершает локальное сохранение; распределённый rollback и удаление созданного пользователя как компенсация запрещены. Транзакция БД не держится во время сетевого запроса. Операции над одной локальной группой сериализуются на уровне сервиса; состояние проверяется ещё раз перед локальным сохранением.

Допущение для первой версии: перенос студента между локальными группами не добавляется. Если code уже связан с другой локальной группой, предварительная проверка или модалка возвращает конфликт до вызова API; администратор сначала исключает его из прежней группы. Другие членства на портале сохраняются. Это согласуется с существующей одной ForeignKey Student.group и не вводит скрытого переноса.

### Импорт и формы

Новый веб-шаблон ориентирован на выбранную группу: обязательные заголовки Фамилия, Имя, Отчество, Почта, code, login, password; значения Отчество, Почта и password могут быть пустыми. code и login обязаны совпадать. Группа и кураторы задаются интерфейсом, поэтому старый многогрупповой консольный шаблон остаётся отдельным. Файл ограничить 5 МБ и 1000 непустых строк, читать openpyxl с запретом формул в полях; коды в шаблоне форматировать как текст. Проверять ФИО, email, длины и уникальность кодов до сетевой записи. Пароль не показывать в предпросмотре и не хранить в сессии или журнале; подтверждение отправляет исходный файл повторно, а сервер повторно проверяет его.

Выполнение — порциями до 25 строк с результатом каждой строки и возможностью повторить файл. При недоступности API оставшиеся строки порции помечаются невыполненными. В каждой строке используется тот же сервис, что и в модалке. При повторном импорте добавление в другую локальную группу не происходит автоматически. Модалки возвращают ошибки внутри формы, сохраняют введённые несекретные поля и блокируют двойное нажатие; серверная идемпотентность остаётся обязательной.

### Проверки

Django-тесты с имитацией API: права, CSRF, формы, XLSX и ведущие нули, обновление без пересоздания Student, таймаут после удалённого успеха, сбой локальной БД и повтор, частичный импорт, исключение без потери TaskAttempt. Контрактные проверки API в тестовой среде WebSoft: повтор и параллельный upsert, пароль без изменений, сохранение других членств, отсутствие назначения семестров, запрет чужих операций и непустой группы. Для API выделить тестовые коды и учётную запись; проверки не использовать для массового изменения боевых данных.

## Risks / Trade-offs

- [Нет общей транзакции] → честные незавершённые состояния, повтор по ключу и сохранение результатов пользователя.
- [Дубли исторических ключей портала] → 409 с диагностикой, без автоматического слияния.
- [Специфика блокировок WebSoft] → обязательная проверка выбранного примитива и конкурентный тест перед приёмкой API.
- [Долгий импорт] → ограничение размера, порции и отдельные результаты; очереди задач пока не требуются.
- [CP1251 API и русские данные] → сохранить кодировку исходников, проверить JSON UTF-8 и русские ФИО на стенде.
- [Незавершённый stash merge в russ_lang] → не затрагивать конфликтующие api/reading_check.py и tasks/api-config.js; их исправление вне change, но конфликты могут мешать общей проверке приложения.

## Migration Plan

1. Реализовать и проверить новые API-маршруты в отдельном репозитории, затем развернуть их с ограниченной авторизацией интеграции.
2. Применить аддитивные миграции russ_lang, не отправляя старые записи на портал; настроить URL и токен вне репозитория.
3. Включить интеграцию после проверки на тестовых кодах; проверить модалки, импорт и безопасный повтор. При отсутствии конфигурации новые операции записи завершаются понятной ошибкой, не переходят к локальной записи.
4. Для отката отключить новые операции управления и вернуть приложение, сохранив аддитивные поля и уже созданные записи портала. Не удалять пользователей и результаты автоматически.
