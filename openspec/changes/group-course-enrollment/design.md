# Design

## Context

Мотивация и границы — proposal.md. Course хранит только name; Group пока не связан с Course. Основной курс создаёт courses/course_sync.py через sync_russian_course, отдельный seed_ai_test_data создаёт тестовый ИИ-курс. Их нельзя сопоставлять по первому попавшемуся ID.

students/roster.py уже объединяет создание пользователя, членство и локальное сохранение; им пользуются модалки и веб-импорт. Запросы идут через students/portal.py на /_wt/russian_language/action/{action}, используя отдельную авторизацию интеграции. Операции Django сериализуются блокировкой ОС, WebSoft — EvalCs. Реализованный change portal-group-student-management остаётся основой; его файлы в этом change не переписываются.

В исходниках установленного WebSoft wtv/wtv_tools.xml функция activate_course_to_person сначала ищет активное обучение и возвращает его ID. Проверка архивных learnings зависит от дополнительных параметров: одного повторного вызова с двумя аргументами недостаточно для гарантии сохранения завершённого курса. В API уже есть примеры вызова этой функции в libs/pk.js, но сценарий ДОТ/семестров не используется.

## Goals / Non-Goals

**Goals:** расширить общий путь сохранения студента и группы назначениями курсов; восстанавливать частично выполненную операцию повтором; не менять существующие обучения.

**Non-Goals:** двусторонняя репликация каталога, отзыв обучения, фоновая очередь и автоматическая синхронизация после произвольного изменения БД. Изменение ID у Course в Django admin само по себе не запускает массовое назначение: повторное сохранение группы или студента использует актуальную привязку. Отчёты и доступ к локальным заданиям не фильтруются новым списком в рамках этого change.

## Decisions

### Модели и начальная привязка

Course.websoft_id — nullable уникальный CharField(max_length=32) с label «ID WebSoft» и проверкой положительного числового ID в диапазоне WebSoft int64. Строковое хранение сохраняет точность на границе JSON/JavaScript. Пустая строка нормализуется в NULL. Администратор редактирует поле в существующем CourseAdmin; отдельный каталог курсов не создаётся.

Group.courses — ManyToManyField('courses.Course', blank=True), с ленивой ссылкой из-за существующего импорта Student в courses/models.py. Новые группы могут иметь пустой набор, чтобы сохранить совместимость прежнего управления; историческим группам миграция курсы не добавляет.

Аддитивная миграция привязывает только единственный существующий курс с точным именем COURSE_NAME из courses/course_sync.py к строке 7221015156608859696. Если основной курс ещё не создан, миграция не создаёт пустой дубликат: обновлённый sync_russian_course заполняет ID при его создании. Несколько совпадений или противоречащая привязка — явная ошибка, а не выбор произвольного курса. Повтор команды сохраняет существующие уроки, задачи и попытки. Отдельный тестовый seed не получает этот ID автоматически.

### Форма группы

Добавить в GroupForm выбор нескольких курсов и отображение выбора при редактировании; в списке групп показать названия выбранных курсов с prefetch_related. Курсы без websoft_id видны в локальном каталоге, но форма отвергает их выбор с сообщением до вызова API. Имена курсов и ID показываются администратору; сетевые реквизиты остаются серверными. XLSX-шаблон студентов не меняется: курс определяется группой, не строкой файла.

### Контракт назначения

Добавить защищённый маршрут `POST /_wt/russian_language/action/ensure_course_assignments` в тот же самостоятельный обработчик авторизации index.html и allowlist интеграции. Тело:

```json
{"group_code":"RU01","student_code":"001","course_ids":["7221015156608859696"]}
```

Один запрос обрабатывает одного студента и текущий список курсов. Для группы Django обходит студентов последовательно; это не удерживает глобальную критическую секцию WebSoft сразу на всю группу. Пустой список обрабатывается локально без запроса. Повторяющиеся ID в запросе нормализуются в один, нечисловые/выходящие за int64/переданные JSON-числом отклоняются. API заранее проверяет существование всех курсов, пользователя с code = login, принадлежность группы области русского языка и членство пользователя; до завершения этой проверки назначений нет.

Успех:

```json
{"ok":true,"data":{"status":"updated","complete":true,"student_id":"...","assignments":[{"course_id":"7221015156608859696","learning_id":"...","status":"created"}]}}
```

Для уже имеющегося обучения status пары = unchanged; общий status = updated при хотя бы одном новом назначении, иначе unchanged. Все ID — строки. Частичный результат возвращает тот же конверт с complete=false и элементами status=error, безопасным code/message. Django проверяет полноту ответа по каждому запрошенному course_id, трактует complete=false и отсутствующие результаты как незавершённую операцию, не скрывая успешные пары. Секреты и внутренние исключения не передаются клиенту. Общие ошибки входа используют прежние 400/401/403/409; потеря ответа остаётся неопределённым результатом.

Альтернатива расширять upsert_student назначениями отвергнута: явный отдельный маршрут удобен для доназначения группе без изменения профилей и паролей. Batch всей группы не вводится, чтобы не держать одну большую операцию WebSoft.

### Использование штатного назначения

Для каждой пары под EvalCs сначала проверить active_learnings, затем learnings. Если есть активное или завершённое обучение — вернуть его ID, ничего в нём не меняя; архивное неуспешное обучение также не перезапускается автоматически. Только при отсутствии обоих вызвать tools.activate_course_to_person с объектом параметров iPersonID, iCourseID и bSendNotification=false. Параметры семестров, дисциплин и перевода не используются. Системные письма/уведомления не отправляются в этом change.

Проверка и создание пары выполняются в одной критической секции. Саму штатную функцию дополнительно не переписывать. Совместимость объектной формы параметров и отсутствие повторного активирования завершённого обучения проверяются на локальном WebSoft с собственными тестовыми записями до приёмки.

### Порядок записи и повтор

Сохранение студента: проверить локальные данные и ID всех выбранных курсов → upsert пользователя и группы → ensure_membership → ensure_course_assignments → локальное сохранение. Обновление профиля использует тот же путь, поэтому довыдаёт пропущенные назначения. Статус строки импорта становится updated также при добавлении курса к неизменившемуся профилю. При ошибке назначений пользователь/членство на портале могут уже существовать; не удалять их как компенсацию. Повтор завершает недостающие шаги и сохраняет прежние результаты.

Сохранение группы: проверить весь желаемый набор → upsert_group → для каждого текущего локального студента обеспечить пользователя/членство прежним механизмом и выдать все курсы желаемого набора → после подтверждения всех студентов локально сохранить группу, кураторов и M2M. Повтор всегда сверяет весь желаемый набор, а не только разность старых и новых: иначе при частичном сбое недостающий курс можно пропустить. Использовать внутренние функции без повторного захвата нерекурсивного roster_lock.

Если студенты исторически ещё не связаны с порталом, применяется обычный общий путь upsert по коду, без сброса пароля существующей записи. Поля модели студента берутся из сохранённых локальных данных. Случайный пароль генерируется только для создания отсутствующего пользователя по прежним правилам.

При частичной ошибке локальный набор курсов остаётся последним полностью подтверждённым; связанная форма сохраняет отправленный выбор, показывает студента/курс и поясняет, что часть удалённых операций могла выполниться. Повторить то же сохранение безопасно. Для нового объекта, который при этом уже появился на портале, повтор находит его по code. Смена желаемого набора между повторами не отменяет уже выполненные назначения.

Удаление курса из выбора и исключение студента не вызывают API отзыва. Они меняют только текущую локальную политику выдачи; уже созданные обучения остаются. Миграции и seed не выполняют удалённые вызовы.

## Risks / Trade-offs

- [Частично выполненная запись в двух системах] → ответы по курсам, отсутствие ложного успеха и повтор всего желаемого набора без компенсационного удаления.
- [Длительное доназначение большой группе] → по одному студенту на HTTP-запрос, отсутствие транзакции БД во время сети, явная ошибка при таймауте и безопасный повтор; фоновая очередь вне этой версии. Проверить время на локальной репрезентативной группе и документировать измерение.
- [Повторное назначение завершённого курса штатной функцией] → проверка обоих каталогов до вызова и отдельный контрактный тест с завершённым обучением.
- [Несуществующий или ошибочно сопоставленный ID] → валидация числовой строки, проверка каталога WebSoft и отсутствие записи при невалидном наборе.
- [Гонка изменения группы и импорта] → прежняя межпроцессная блокировка Django на весь сценарий и EvalCs на каждую пару WebSoft; ограничения одного хоста/экземпляра сохраняются.

## Migration Plan

1. Развернуть и проверить новый API action локально, затем добавить его на целевой портал до включения клиентов с назначениями. Наличие API на production не предполагать по локальному результату.
2. Применить миграции Course.websoft_id и Group.courses; заполнить только основной курс и проверить сохранение локальных ID и результатов. Другие курсы администратор связывает вручную через CourseAdmin.
3. Проверить страницу группы с двумя курсами, создание и импорт студента, добавление курса существующей группе, повтор и снятие курса из текущего набора без отзыва.
4. Для отката вернуть предыдущий клиент/маршруты, сохранив аддитивные поля и уже выданные назначения. Удалять обучения и результаты автоматически нельзя.
